Laravel 13.x — quick guide (aligned with the official documentation)

This section summarizes the main chapters of the Laravel 13.x documentation and collects ready-to-copy commands and snippets.

Getting started

PHP/Composer installation, laravel CLI, app creation with laravel new, startup with composer run dev (server, queue, Vite). Configuration via .env and files in config/. Default SQLite in database/database.sqlite; for MySQL update DB_* and run php artisan migrate.

Architecture

Request lifecycle, service container, providers, facades. Predictable folder conventions for AI agents and tools (see also Agentic development).

The basics

Routing, middleware, CSRF, controllers, requests, responses, Blade, assets with Vite, URL generation, sessions, validation, logging, error handling.

Digging deeper

Artisan, broadcasting, cache, collections, HTTP client, file storage, mail, notifications, strings, queue, rate limiting, scheduling, tasks.

Security & database

Authentication, authorization, hashing, encryption. Query builder, migrations, seeding, Redis, MongoDB. Eloquent: relationships, casts, API resources, factories.

AI & testing

Laravel Boost for AI context (versioned documentation, tools). HTTP, console, browser, database tests, mocking.

Packages

Ecosystem: Horizon, Sanctum, Sail, Telescope, Pint, Passport, Scout, Dusk, Cashier, etc. Each package has its own section in the official docs.

Gherkin — quick guide with examples

Gherkin is the language used in BDD (Behavior-Driven Development) to describe expected behavior in a form readable by both people and tools (Cucumber, Behat, SpecFlow, etc.). Each .feature file describes a capability and its test scenarios.

Keywords

  • Feature — title and description of the capability
  • Background — steps shared by all scenarios (optional)
  • Scenario — a concrete use case
  • Scenario Outline + Examples — same flow with different data
  • Given — preconditions / initial state
  • When — user action or event
  • Then — expected outcome
  • And / But — continue the previous step
  • """ ... """ — doc string for multiline text (JSON payloads, bodies, templates)
  • Data tables (| col | col |) — structured input or expected fields

Basic rules

  • Indentation: usually 2 spaces per level (Feature → Scenario → steps)
  • One scenario = one verifiable behavior; avoid overly long scenarios
  • Write in domain language, not technical details (“the cart is empty”, not “click #btn-42”)
  • Use Given for state, When for action, Then for outcome
  • Comments with #; optional tags above Feature/Scenario: @smoke @checkout

Example 1 — Simple feature

Feature: User login
  As a registered user
  I want to sign in with email and password
  So that I can access my account

  Scenario: Login with valid credentials
    Given I am on the login page
    And a user "alice@example.com" exists with password "secret123"
    When I submit email "alice@example.com" and password "secret123"
    Then I should see the dashboard
    And I should see a welcome message for "Alice"

  Scenario: Wrong password
    Given I am on the login page
    And a user "alice@example.com" exists with password "secret123"
    When I submit email "alice@example.com" and password "wrong"
    Then I should see an error "Invalid credentials"
    And I should remain on the login page

Example 2 — Shared Background

Feature: Shopping cart
  As a shopper
  I want to manage items in my cart
  So that I can buy products

  Background:
    Given I am logged in as "alice@example.com"
    And the following product exists:
      | sku   | name   | price |
      | PEN-1 | Pen    | 2.50  |

  Scenario: Add a product
    Given my cart is empty
    When I add "PEN-1" to the cart
    Then my cart should contain 1 item
    And the cart total should be 2.50

  Scenario: Empty the cart
    Given my cart contains "PEN-1"
    When I remove all items from the cart
    Then my cart should be empty

Example 3 — Scenario Outline (parameters)

Feature: Email validation on registration

  Scenario Outline: Email format
    Given I am on the registration page
    When I enter email "<email>"
    Then I should see validation "<message>"

    Examples:
      | email           | message              |
      | user@domain.com |                      |
      | not-an-email    | Invalid email format |
      |                 | Email is required    |

Example 4 — Tags and Rule (Gherkin 6+)

@checkout @e2e
Feature: Checkout

  Rule: The cart cannot be empty
    Scenario: Attempt with empty cart
      Given my cart is empty
      When I proceed to checkout
      Then I should see "Your cart is empty"

  Rule: Supported payment methods
    Scenario Outline: Accepted payment
      Given my cart total is 10.00
      When I pay with "<method>"
      Then the order should be confirmed

      Examples:
        | method  |
        | card    |
        | paypal  |

Example 5 — REST API with request/response payloads

For API or integration features, assert HTTP status, headers, and JSON bodies explicitly. Use doc strings for payloads; keep step wording stable and map it in step definitions. 

@api @orders
Feature: Create order API
  As an integration client
  I want to create orders via REST
  So that external systems can place purchases

  Background:
    Given the API base URL is "https://api.example.com"
    And I am authenticated with bearer token "svc_orders_writer"

  Scenario: Create order with valid payload
    Given the following product exists:
      | id     | sku   | unitPrice | stock |
      | prod_1 | PEN-1 | 2.50      | 10    |
    When I send a POST request to "/v1/orders" with headers:
      | name         | value            |
      | Content-Type | application/json |
      | Idempotency-Key | idem_abc123   |
    And the request body is:
      """
      {
        "customerId": "cust_42",
        "items": [{ "sku": "PEN-1", "quantity": 2 }],
        "currency": "EUR",
        "shippingAddress": {
          "line1": "Via Roma 1",
          "city": "Milan",
          "country": "IT"
        }
      }
      """
    Then the response status should be 201
    And the response header "Content-Type" should be "application/json"
    And the response header "Location" should match "/v1/orders/*"
    And the response JSON should match:
      """
      {
        "status": "pending",
        "currency": "EUR",
        "total": 5.00,
        "items": [
          { "sku": "PEN-1", "quantity": 2, "unitPrice": 2.50, "lineTotal": 5.00 }
        ]
      }
      """
    And the response JSON field "id" should be a non-empty string

  Scenario: Reject invalid payload with structured error
    When I send a POST request to "/v1/orders" with body:
      """
      { "customerId": "cust_42", "items": [], "currency": "EUR" }
      """
    Then the response status should be 422
    And the response JSON should be:
      """
      {
        "error": "validation_failed",
        "message": "The request could not be processed",
        "details": [
          { "field": "items", "code": "min_items", "message": "must contain at least one item" }
        ]
      }
      """

Example 6 — Pagination, filtering, and partial response match

@api @invoices
Feature: List customer invoices

  Scenario: Paginated invoice list with metadata
    Given these invoices exist for customer "cust_42":
      | id      | amount | status | issuedAt   |
      | inv_101 | 10.00  | paid   | 2026-01-01 |
      | inv_102 | 25.00  | open   | 2026-01-05 |
      | inv_103 | 7.50   | paid   | 2026-01-08 |
    When I send a GET request to "/v1/customers/cust_42/invoices?status=paid&page=1&limit=2"
    Then the response status should be 200
    And the response JSON should match:
      """
      {
        "data": [
          { "id": "inv_101", "amount": 10.00, "status": "paid" },
          { "id": "inv_103", "amount": 7.50, "status": "paid" }
        ],
        "meta": { "page": 1, "limit": 2, "total": 2, "totalPages": 1 }
      }
      """
    And the response JSON path "$.data" should have length 2

  Scenario: Empty result set
    When I send a GET request to "/v1/customers/cust_99/invoices"
    Then the response status should be 200
    And the response JSON should be:
      """
      { "data": [], "meta": { "page": 1, "limit": 20, "total": 0, "totalPages": 0 } }
      """

Example 7 — Webhook ingestion and downstream event

@webhook @payments
Feature: Payment provider webhook

  Scenario: Mark order paid after payment_intent.succeeded
    Given order "ord_99" exists with:
      | field    | value   |
      | status   | pending |
      | total    | 50.00   |
      | currency | EUR     |
    And the webhook signing secret is "whsec_test"
    When the payment provider sends POST "/webhooks/stripe" with signed payload:
      """
      {
        "id": "evt_1N2example",
        "type": "payment_intent.succeeded",
        "created": 1710000000,
        "data": {
          "object": {
            "id": "pi_3Nexample",
            "amount_received": 5000,
            "currency": "eur",
            "metadata": { "orderId": "ord_99" }
          }
        }
      }
      """
    Then the response status should be 200
    And the response body should be empty
    And order "ord_99" should have status "paid"
    And an outbox event "order.paid" should be published with payload:
      """
      {
        "orderId": "ord_99",
        "paymentIntentId": "pi_3Nexample",
        "amount": 50.00,
        "currency": "EUR"
      }
      """

  Scenario: Reject webhook with invalid signature
    When the payment provider sends POST "/webhooks/stripe" with invalid signature and payload:
      """{ "id": "evt_bad", "type": "payment_intent.succeeded" }"""
    Then the response status should be 400
    And the response JSON should be:
      """{ "error": "invalid_signature", "message": "Webhook signature verification failed" }"""

Example 8 — Scenario Outline for auth and error responses

@api @auth
Feature: Protected profile endpoint

  Scenario Outline: Authorization failures return consistent error shape
    When I send a GET request to "/v1/me" with headers:
      | name          | value           |
      | Authorization | <authorization> |
    Then the response status should be <status>
    And the response JSON should be:
      """
      <response_body>
      """

    Examples:
      | authorization        | status | response_body                                                                 |
      |                      | 401    | {"error":"unauthorized","message":"Missing bearer token"}                     |
      | Bearer bad.token     | 401    | {"error":"unauthorized","message":"Invalid token"}                            |
      | Bearer expired.jwt   | 401    | {"error":"unauthorized","message":"Token expired"}                            |
      | Bearer valid.jwt     | 200    | {"id":"usr_1","email":"alice@example.com","roles":["user"]}                   |

Example 9 — GraphQL query with variables and errors

@api @graphql
Feature: Order lookup via GraphQL

  Scenario: Successful query with variables
    Given order "ord_77" exists with status "shipped" and total 19.99
    When I send a POST request to "/graphql" with body:
      """
      {
        "query": "query ($id: ID!) { order(id: $id) { id status total currency } }",
        "variables": { "id": "ord_77" }
      }
      """
    Then the response status should be 200
    And the response JSON should match:
      """
      {
        "data": {
          "order": { "id": "ord_77", "status": "shipped", "total": 19.99, "currency": "EUR" }
        }
      }
      """
    And the response JSON path "$.errors" should be absent

  Scenario: GraphQL validation error
    When I send a POST request to "/graphql" with body:
      """
      { "query": "query { unknownField }" }
      """
    Then the response status should be 200
    And the response JSON path "$.data" should be null
    And the response JSON path "$.errors[0].message" should contain "Cannot query field"

Anti-patterns to avoid

  • Identical steps repeated in every scenario → use Background
  • Too many consecutive And steps → split into smaller scenarios
  • In UI specs, avoid low-level selectors or raw HTTP codes → describe user-visible outcomes
  • In API specs, do assert status and payload — but keep steps reusable (don’t paste unique URLs in every step)
  • Huge JSON blobs inline in step text → prefer doc strings or external fixture files referenced by step defs
  • One scenario describing multiple unrelated behaviors
